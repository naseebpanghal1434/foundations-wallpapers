SystemHome timeline · k-way merge

The feed is a mix, not a query.

Home feed is not SELECT * FROM posts WHERE author IN (friends) ORDER BY ts — that is scatter-gather every scroll. Mix: friends inbox + celeb pulls + ads, k-way merge (heap of k heads, plate 161), cache the first 50, cursor (ts, id).

Gather the sourcesFriends inbox (fan-out on write). Celeb pulls (plate 203). Ads. A seen-id Bloom / Redis set (plate 123) so the same post does not loop.

Merge by score / tsHeap of k heads, O(n log k). Ranking is a model; correctness is don’t miss, don’t dup. Unfollow invalidates the cache, it does not rewrite 80M inboxes.

3

Cache page 1, cursor the restFirst 50 in Redis ~60 s. Cursor = last (ts, id), never OFFSET (plate 32). Next scroll is the cursor, not a full recompute.

50
What

Feed = mix of streams + rank + cache + cursor. Pagination is the cursor. Deletes / unfollows are invalidations, not instant global rewrites.

Why

News-feed design. They watch for one SQL IN-list. Say mix, cache first 50, cursor (ts,id).

Trap

OFFSET on a live feed — items shift, dups and holes. Recomputing the whole mix on every scroll. No seen-set so the same post loops.
