BackendLIMIT/OFFSET · keyset

Offset pagination lies.

LIMIT 20 OFFSET 10000 makes the engine walk 10,020 rows and discard 10,000. Cost is O(offset + limit), not O(limit). Inserts at the top skip and duplicate rows across pages. Keyset: continue from a unique sort key — O(log n + 20) with that index.

Page 501 of a feed

OFFSET

SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 10000 -- still walks 10020 rows INSERT at top: page 2 repeats, page 3 skips

Fine for an admin UI of 50 rows. A live feed plus deep OFFSET is both slow and wrong.

vs

Seek the next key

Cursor

WHERE (created_at, id) < ($t, $id) ORDER BY created_at DESC, id DESC LIMIT 20 INDEX (created_at, id) next = last row’s (t, id)

Keyset pagination. GraphQL after: cursor is this. No skipped work. Inserts don’t shuffle pages.

What

Offset = skip N. Cursor = bookmark on a unique sort key (tie-break with id). Postgres still walks OFFSET even with an index. Encode the key, not a page number, as the “cursor.”

Why

Deep offsets get slower linearly. Live lists change under you. Every product has a list; OFFSET is what people write first. Interviews want the index and the skip/dup bug.

Trap

Cursor on a non-unique column (ties skip rows). Page number base64’d and called a cursor. SELECT COUNT(*) on 50M rows every page — don’t, or cache an estimate.
