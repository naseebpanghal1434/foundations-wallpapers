Language8 MiB stack · malloc/mmap

Frames die. Heap objects live.

A call pushes a stack frame (return address, saved frame pointer, locals) and return pops it. Linux default pthread stack is 8 MiB; x86-64 stacks grow down. Heap objects come from malloc / brk / mmap / new and outlive the frame until nothing points at them (plate 70). Never return &local — that address is junk after the pop.

Stack

8 MiB

Per thread. LIFO frames. Allocation is add to RSP. Gone on return. C: int x lives here.

Heap

brk / mmap

User, arrays, closures. Lifetime is reachability (or free). The binding p was in the frame; the object is here.

Frame

RIP · RBP

Return address, saved RBP, args, locals. Recursion (plate 56) is this stack, not the heap data structure (plate 52).

C bug

return &x

int *f(){ int x=1; return &x; } — use-after-return. JS will not give you that address.

What

Stack = per-call storage, popped on return. Heap = objects whose lifetime is reachability. Closures move captured bindings onto the heap (plate 23). A binary heap is a third word (plate 63).

Why

Explains mutation vs copy (plate 68) and why a returned inner function still sees count. Interviews want the picture, then the C dangling pointer.

Trap

Answering “what’s a stack?” with heap-vs-stack memory when they wanted LIFO (plate 52) — or the reverse. Also: treating JS numbers as heap boxes; engines tag small ints.
