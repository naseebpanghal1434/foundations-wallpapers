System~1–3 µs · CR3 · TLB

Save the registers. Restore later.

A context switch parks one thread and runs another: save GPRs, RIP, RSP, RFLAGS (and FPU). Same mm_struct: about 1–3 µs. Different process: also load CR3, TLB shootdown (plate 79). 10 000 kernel threads with 8 MiB stacks is 80 GiB of virtual memory and a cold cache. Linux CFS picks the next runnable.

Workers ≈ cores · many fds

A pool

8 workers · 8 cores 10_000 connections wait on epoll / kqueue run queue ≈ 8 stack: 8 × ~8 MiB switch when a worker blocks

Blockers (disk, DNS, a mutex) still need extra threads. The number is a budget, not “one per client.”

vs

One OS thread per connection

10k threads

10_000 threads 10_000 × 8 MiB stacks run queue: thousands mostly save / restore cache cold, TLB cold CPU busy, little work

Direct cost is microseconds. Indirect cost is the 64 B cache lines you just threw away.

What

Scheduler picks a new thread. Voluntary (blocking I/O, futex wait) or preemptive (timeslice). Same process is cheaper than a process switch. User-space fibers still yield; they just skip the kernel path.

Why

You need switches to share a core. You do not need one kernel thread per connection. Interviews: name what is saved, say the cache tax, size the pool to cores plus blocking.

Trap

10k threads for 10k connections — thread-per-request until the machine spends its time switching. More threads is not more throughput once the run queue is the product.
