DSACollisions · load factor

Hash into buckets.

A hash function turns a key into a bucket index. Two keys can land in the same bucket — a collision. Load factor is items ÷ buckets; when it climbs, you resize. Average get/put is O(1). That is a promise about the average, not a law.

Key → index

Hash

h = hash("ada") % 8 table[h] holds "ada"

Need hash and equals. Same hash ≠ same key — then you compare.

Two keys, one slot

Collide

bucket[3]: ada → 7 kai → 2 chain

Chaining (list/tree) or open addressing (probe the next empty slot).

n / buckets

Load

6 / 8 = 0.75 resize → 16 rehash every key

Java’s default 0.75, then ×2. Resize is O(n), amortized into the puts.

What

Set / map / dict. Average O(1) get, put, delete. Worst O(n) if everything collides. Iteration is O(n) in the items — looking the map up once is not “looping it is free.”

Why

2-sum, counting, grouping, “have I seen this?” SDE-1 default for lookup. Say: hash → bucket → equals on the chain. That’s the whole machine.

Trap

Mutable keys: hash, then change a field the hash used — the entry sits in the old bucket, get misses. Assuming O(1) always (adversarial hashes, one giant chain). Using a list as a key (Python won’t; Java will hurt you).
