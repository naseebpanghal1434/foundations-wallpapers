DatabaseBLCKSZ · shared_buffers

Postgres reads 8 KiB pages, not rows.

Heap and indexes are arrays of 8192-byte pages (BLCKSZ). A seq scan is page I/O. shared_buffers caches those pages (often ~25% of RAM). A row lives in a page behind an ItemId; an UPDATE leaves a new tuple version (plate 96, 351).

BLCKSZ

8 KiB

I/O unit. Header + ItemId[] + free + tuples. Not “a row.”

TOAST

~2 KiB

Wider values leave the page. The heap keeps a pointer.

shared_buffers

~25% RAM

Postgres page cache. Leave RAM for the OS cache too.

work_mem

per sort

Each backend × each sort/hash. Not a global budget.

EXPLAIN (ANALYZE, BUFFERS) counts hits/reads (plate 98). Fillfactor leaves air on the page for HOT (plate 350).

What

The I/O unit is the page. Row count is a consequence of packing. Random updates dirty many pages; appends dirty the right edge.

Why

Tuning, bloat, why a 1-byte SET still writes 8 KiB. Shared buffers vs OS cache is the RAM split.

Trap

shared_buffers = all RAM (no OS cache, no connections). Counting rows as I/O. Ignoring TOAST on wide JSON.
