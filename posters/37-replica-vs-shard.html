SystemWAL stream · hash(key)%N

Copy the data, or split it.

Replica: the same bytes on more nodes. Writes go to one primary; replicas apply WAL (Postgres streaming, MySQL binlog). Reads scale with replica count; lag is ms–s. Shard: each node owns a slice — hash(user_id) % N or a range. Writes scale with N; a cross-shard JOIN is a product problem.

What

Replica = copies. Shard = partitions. You often do both: each shard has a primary + replicas. Citus / Vitess / Redis Cluster. Consistent hashing (plate 91) reduces how many keys move when N changes.

Why

Read-heavy: replicas first. Write-heavy or data bigger than one disk: shard. Default “scale the database” interview fork.

Trap

Sharding on email then needing “all users in IN.” Hot shard (celebrity user_id). Reading a replica then writing as if it was current. Replicas are not a backup unless you test restore.
