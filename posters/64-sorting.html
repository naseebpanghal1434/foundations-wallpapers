DSAWorst case matters

n log n, or n squared.

Comparison sorts cannot beat n log n in the worst case: you need that many yes/no questions. Insertion, selection, bubble are O(n²). Merge, heap, and average quicksort are n log n. Radix and counting skip comparisons and can be linear in n. Quicksort’s worst case is still n² — it is not “always fast.”

Nested loops

n²

Insertion, selection, bubble.
Insertion: fast on tiny / nearly sorted.
n = 10⁵ → ~10¹⁰ ops. Too slow.

Fine for n ≤ a few thousand, or as Timsort’s inner pass.

The default answer

n log n

Merge: always, extra array, stable.
Heap: always, in-place, not stable.
Quick: avg n log n, in-place, not stable.

Library sort is this family (often Timsort / introsort).

Not comparison

O(n)

Counting: small integer range.
Radix: digits / bytes, O(n · digits).
Only when the keys look like integers.

Beats n log n when the model fits. Not for arbitrary objects.

What

Know worst / extra space / stable for four names: quick, merge, heap, radix. Quick: pick a pivot, partition, recurse. Sorted input + pivot = first element → n². Fix: random pivot, median-of-three, or introsort (switch to heap). Java ints: dual-pivot quick; objects: Timsort.

Why

n = 10⁵ is the usual hidden constraint. n² dies, n log n passes. If they only need k largest, don’t sort n (plate 63). If they only need a boolean “can we sort to target,” maybe you don’t sort at all.

Trap

Calling quicksort always-fast: worst case is n², and adversarial / already-sorted data hits it without randomization. Also: radix on generic Comparable. Also: “merge is n²” (it is not).
