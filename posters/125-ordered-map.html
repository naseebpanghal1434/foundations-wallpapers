DSATreeMap · floor · ceiling

Keys stay sorted.

An ordered map keeps keys in sorted order. Lookup is O(log n), not O(1). You gain predecessor, successor, range. Java TreeMap, C++ map, Python SortedDict — usually a balanced BST (plate 113) or a skip list (plate 124). A HashMap has none of the order ops.

Exact key only

HashMap

get / put O(1) avg no floor no ceiling no in-order walk

Two-sum, counting, “have I seen this?” Plate 51. Order is not the job.

Nearest key · range

TreeMap

floor(x) greatest ≤ x ceiling least ≥ x first / last submap [a, b]

Insert / erase / get O(log n). Range iterate O(log n + k).

Same idea, list of ts

Timestamps

key → sorted ts binary search the time (plate 198) floor = last ≤ t

Iterate keys in order without a separate sort. Nearest, not exact.

What

floor = greatest key ≤ x. ceiling = least key ≥ x. Insert/erase/get O(log n). Range iterate O(log n + k). The keys stay sorted because the tree (or skip list) maintains that invariant on every write.

Why

Leaderboards, time-based KV, “next interval,” sliding-window medians with two trees, exam room / flowers at t. When the problem says nearest key, not exact key — that is the fork from HashMap.

Trap

Using TreeMap for two-sum — log n for no reason. Assuming Python dict is ordered by key (it is insertion-ordered, not sorted). Mutating a key that participates in compare — it sits in the wrong place, same class of bug as a mutable hashmap key (plate 51).
