FrontendSearch box vs scroll

Debounce waits. Throttle caps.

Both cut down how often a function runs. Debounce: run once the events have stopped. Throttle: run at most once per time window, even if events keep coming.

Typing in search

Debounce

keys: a a a a a a a fire: ■ wait 300ms quiet
Reset the timer on every keystroke.
One request after they pause.
Use for search, resize-end, save-draft.
vs

Scroll / mousemove

Throttle

scroll: ■ ■ ■ ■ ■ ■ ■ ■ fire: ■ ■ ■ at most every 100ms
First (or last) event in each window.
Still updates while they keep scrolling.
Use for scroll, pointer, infinite list.
What

Debounce = “wait until quiet.” Throttle = “at most once per N ms.” Both need leading/trailing choices (fire at start, end, or both).

Why

A search box that fetches on every key hammers the API. A scroll handler that computes layout 60 times/frame janks. These are the two standard answers.

Trap

Using debounce on scroll (the UI freezes until you stop). Using throttle on search (you search for “a”, “ap”, “app”…). Also: forgetting to cancel on unmount.
