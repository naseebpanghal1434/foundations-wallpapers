Random UUIDs as PKs scatter the B+tree.

A btree inserts at the rightmost leaf if keys increase (identity, snowflake plate 93, ULID, uuid v7). uuid4 is random: each insert splits a random leaf, dirtying many 8 KiB pages, killing cache. Fine for small tables; painful at 1e8 rows.

Need an unguessable public id? Secondary unique, not the PK (plate 100).

What

Index locality follows key order. Random PKs randomize writes. uuid4 also widens every secondary index that includes the PK.

Why

Write amplification, index bloat, checkpoint I/O. The B+ wants append (plate 337), not scatter.

Trap

uuid_generate_v4() as PK on a hot events table. v1/v4 “because UUID.” v7 exists; use it if you must have a UUID.
