DatabaseB-tree · 8 KiB pages

An index is extra storage.

A B-tree index is a second on-disk structure: ordered keys plus row pointers (ctid in Postgres). Heap pages are 8 KiB. Fanout ~100–300 keys/page, so 1e6 rows is height 3–4 — O(log n) seeks, not O(n) heap reads. Every INSERT/UPDATE/DELETE maintains the tree.

WHERE email = $1 · no index

Seq Scan

EXPLAIN ANALYZE Seq Scan on users rows=1e6 actual time=12..840 ms Filter: email = 'ada@…' Buffers: shared read=12500

Walk every 8 KiB heap page. 1e6 × 100 B ≈ 100 MiB. Cost grows with table size, not selectivity.

vs

CREATE INDEX ON users (email)

Index Scan

Index Scan using users_email_idx actual time=0.04..0.18 ms rows=1 loops=1 Index Cond: email = $1 Buffers: shared hit=4

Descend the btree, then heap fetch by ctid. Covering index / INCLUDE → Index Only Scan, skip the heap (plate 97).

What

Heap = the table. Index = (key → ctid) btree. Planner may still Seq Scan if it expects most rows. EXPLAIN ANALYZE (plate 98) is the proof.

Why

WHERE email = $1 on 1e6 rows is ~800 ms sequential vs sub-ms seek. Unique indexes also enforce uniqueness.

Trap

An index per column: each btree is write amplification on every INSERT. Low-cardinality flags are ignored. WHERE a AND b needs a composite, not two separate trees (plate 97).
