Databasecost · random_page_cost

Seq scan is n pages. Index is log n then heap.

Seq scan: read every heap page, cheap sequential I/O. Index scan: B+ lookup (height 3–4) plus one heap fetch per row — random. Planner cost ≈ pages × random_page_cost (4 on HDD, ~1.1 on SSD). Selecting 30% of the table? Seq often wins.

1e7 rows · 1e5 pages

Seq Scan

read page 1 read page 2 … read page 1e5 seq_page_cost = 1.0 filter after the read

One sequential pass. Fine when you need most of the heap anyway.

vs

50 rows from an index

Index Scan

3 index pages (height) + 50 heap pages (random) random_page_cost 4.0 HDD default 1.1 SSD hint

Bitmap index scan batches those heap fetches (plate 340). ANALYZE feeds the guess (plate 98).

What

The cheaper plan is selectivity × I/O randomness, not “index always.” Covering indexes skip the heap (plate 349).

Why

Why an index sits unused. Why random_page_cost still at 4 on NVMe makes indexes look expensive.

Trap

Index on a boolean 50/50. SELECT * so the index is not covering and you heap-fetch anyway. Stale stats: estimated 5e5, actual 12.
