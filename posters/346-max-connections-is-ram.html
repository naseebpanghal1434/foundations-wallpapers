Databasework_mem · 100 not 10000

max_connections is RAM. Pool in the app.

Each Postgres backend is a process (~5–15 MiB idle + work_mem per sort). 5000 connections = tens of GiB plus context-switch death. PgBouncer / the app pool (plate 3) in transaction mode. Default max_connections 100 is a hint, not a dare.

default

100

max_connections. Raise it and you buy RAM and scheduler noise.

idle backend

5–15 MiB

One process per connection, before any sort. Not a thread.

work_mem

4–64 MiB

Per sort/hash, per backend. 100 × 64 MiB = 6.4 GiB if all sort.

pool

PgBouncer

Transaction mode multiplexes. RDS formulas still want a pooler.

Serverless frontends that open a conn per invoke skip the pool and then hit too many clients at 3am.

What

Process-per-connection. Multiplex at the pool so 5k HTTP handlers share ~50 backends. Idle still costs RAM (plate 3).

Why

The 3am too-many-clients plus OOM. Connection count is a memory budget, not an app-server count.

Trap

Raising max_connections to match the app-server farm. Session-mode pooling with 5k clients anyway — you just moved the herd.
