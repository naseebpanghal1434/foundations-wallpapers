BackendGET · SET · DEL · TTL

The cache is a rumor.

A cache is a derived copy (Redis STRING, process LRU) of a database row. GET is ~0.2–2 ms vs 5–50 ms SQL. EXPIRE bounds staleness; it does not update the copy. Cache-aside: GET, on miss SELECT then SET. On write: UPDATE the row, then DEL the key.

Read · cache-aside

GET user:7 → "…json…" hit ~0.3 ms → (nil) miss SELECT * FROM users WHERE id = 7 8 ms SET user:7 $row EX 60

TTL is a cap (60 s), not invalidation. Jitter EX 60+rand(10) so keys do not expire together (plate 94).

write

Write the row, then delete

DEL user:7

UPDATE users SET email=$1 WHERE id = 7; DEL user:7 next GET refills from the row do not SET the new value here

A crash after UPDATE and before DEL leaves a stale key until TTL. Stampede on expiry: lock / singleflight (plate 94).

What

Cache-aside: fill on miss, DEL on write. Source of truth is the row. Redis is O(1) per key, not a second database of record.

Why

Hot keys: 5k rps × 10 ms SQL = 50k QPS on one row. Redis absorbs repeats. Interviews: name the invalidation.

Trap

SET on write (dual-write) — crash between DB and Redis leaves a new stale value with a fresh TTL. TTL-only: user changes email, cache serves the old one for 60 s. Filling from a lagging replica.
