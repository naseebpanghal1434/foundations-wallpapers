LangAOT · VM · hot path

Compile ahead. Interpret each form. JIT both.

AOT (C, Go, rustc): translate to machine code before run — 0 warmup, one ISA’s binary. Interpreter (CPython’s ceval.c loop, early Java): execute each bytecode form; portable, ~10–100× a C loop. JIT (V8, HotSpot, LuaJIT): interpret or baseline first, then emit native for hot functions using types you observed.

Before run

AOT

gcc -O2 / rustc / go → ELF · Mach-O · PE native for one CPU 0 warmup

-O0 is still compiled. It is not optimized.

Each form

Interpret

.pyc → ceval.c LOAD_FAST, BINARY_OP portable bytecode ~10–100× C

The inner loop is a VM dispatch, not a native add.

Hot path

JIT

V8 Ignition → TurboFan HotSpot C1 / C2 specialize on types deopt if they change

Graal, PyPy, JavaScriptCore: same shape (plate 336).

What

When machine code is produced. AOT: compile time. Interpreter: every opcode. JIT: after warmup, speculative native that can deoptimize if types change.

Why

Why a tight Python loop is slow and the C rewrite is not. Why a JVM bench needs 10–30 s warm and -XX: flags, not one call.

Trap

Benchmarking a JIT with one iteration (you timed the interpreter). Shipping CPython on a 1 ms p99 path. Assuming “compiled” means optimized (gcc -O0).
