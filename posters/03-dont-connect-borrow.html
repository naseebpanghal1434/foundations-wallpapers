Backendmax_connections · pool

Don't connect. Borrow.

A Postgres session is TCP + TLS + StartupMessage + a backend process (~5–10 MiB RSS). That is 2–3 RTTs (~1–10 ms LAN, 50–200 ms WAN) plus fork. A pool (PgBouncer, node-pg, HikariCP) keeps N sockets open; checkout is a mutex, not connect().

PQconnectdb per request

connect()

SYN + TLS 1.3 StartupMessage + auth backend fork ~5–10 MiB SELECT … 0.4 ms PQfinish → tear down 2–3 RTT before SQL FATAL 53300 if over max

max_connections default 100. Each idle backend still costs RAM and a slot.

vs

Pool max 20 · PgBouncer

checkout

pool.acquire() PQexec SELECT … pool.release() session already live SQL is most of the time 3 apps × max 50 = 150 > 100 → 53300

Transaction pooling: many clients, few backends. Release on the error path too.

What

Checkout a live connection, run SQL, release. Postgres: one backend per live session. PgBouncer multiplexes clients onto fewer backends.

Why

Tail latency is often connect(), not the SELECT. The database’s connection cap is a hard error, not a slowdown.

Trap

Pool max × app replicas > max_connections → SQLSTATE 53300. Holding a checkout across an outbound HTTP call. Leaking SET / temp tables onto the next client if you skip release.
