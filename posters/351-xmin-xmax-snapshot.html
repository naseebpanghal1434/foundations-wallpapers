DatabaseMVCC · xmin xmax

A tuple is (xmin, xmax). Readers see a snapshot.

Heap tuple header: xmin = creating xid, xmax = deleting/updating xid (0 if live). A snapshot is the set of in-progress xids + xmax. The reader sees the version where xmin committed before the snapshot and xmax did not. No row lock for readers (plate 96).

T1 UPDATE, T2 SELECT

Old xmin

Ada v1 xmin=10 xmax=40 Ada v2 xmin=40 xmax=0 T2 snapshot 10..39 HeapTupleSatisfiesMVCC still sees v1 T1 not committed T2 does not wait

Writers still set xmax. Writers still block writers on the same row. MVCC is not “no locks.”

vs

T1 COMMIT, next snapshot

New xmin

T1 commit next snapshot sees v2 READ COMMITTED new snapshot per stmt REPEATABLE READ one snapshot (plate 40) long T2 keeps v1 until T2 ends → bloat (plate 341)

32-bit xid on the tuple is why freeze exists (plate 342). A 4-hour report is a vacuum problem.

What

Visibility is per-tuple metadata, not a lock. Writers set xmax. HeapTupleSatisfiesMVCC is the predicate.

Why

READ COMMITTED vs REPEATABLE READ is which snapshot you hold (plate 40). That is the isolation letter, not a different storage format.

Trap

A 4-hour report transaction pinning xmin. SELECT FOR UPDATE when you only needed a snapshot. Lost updates still happen without a lock or version column.
