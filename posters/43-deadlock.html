Database40P01 · lock order

Deadlock is a cycle of waits.

Deadlock is a cycle in the wait-for graph. Txn A holds row 1, wants row 2; B holds 2, wants 1. Postgres aborts a victim: 40P01 deadlock_detected. Retry the victim. Prevent it by locking rows in one order (ORDER BY id) and keeping transactions short — no HTTP while holding a row lock.

Transfer both ways at once

Cycle

A: SELECT FOR UPDATE Ada then Kai B: SELECT FOR UPDATE Kai then Ada wait → wait → wait ERROR: 40P01 deadlock_detected

The abort is a feature. Catch 40P01, backoff, retry B. innodb_deadlock vs lock wait timeout are different.

fix

Always smaller id first

One order

ids = sorted(Ada.id, Kai.id) LOCK min then max A and B take Ada first B waits on Ada no cycle SET lock_timeout = '2s'

Same rule in every code path. Short txns. Don’t wait on Stripe while holding locks.

What

Wait-for cycle on row or relation locks. Detection is graph-based; lock timeout is the dumb cousin. Also: two advisory locks, or FK checks locking parent rows in opposite order.

Why

Any app that updates two rows in different orders will hit this in production. Interviews want: detect, abort, retry, lock order, keep txns short.

Trap

Treating deadlock as a crash. Catch and retry with jitter. Don’t hold FOR UPDATE across a network call. Don’t mix lock orders across services.
