BackendRPC wait · queue ack

Call, or leave a message.

REST and RPC block on recv until a status or timeout (20–200 ms typical). A queue (SQS, Kafka, Redis Streams, AMQP) is persist-then-ack: produce returns when the broker has the bytes; a worker consumes later. At-least-once is the default (plate 92).

Nouns · HTTP

REST

GET /orders/12 → 200 POST /orders → 201 DELETE /orders/12 → 204 caller waits 1 RTT + handler
Cacheable GETs. HTTP status is the contract (plate 34).
Callee down → 502/503/timeout now.

Public APIs, CRUD.

Verbs · protobuf / JSON

RPC

createOrder({sku, qty}) grpc: HTTP/2 + proto deadline 200ms still a blocking call
Tight contract. gRPC status, not only HTTP.
Internal services, unary or stream (plate 282).

Sync service-to-service.

Persist · ack later

Queue

PUBLISH order.created {id:12, qty:2} → 202 to the client worker: consume, ack retry on nack
Producer does not wait on billing.
Consumer can be at 0 replicas right now.

Email, webhooks, thumbnails.

What

A call couples you to a live callee and a deadline. A message couples you to a durable log and an ack protocol.

Why

Checkout total → call. Send receipt → queue. If billing is down, the order row can still commit and the worker retries.

Trap

Enqueue then poll /jobs/:id every 50 ms — a slow RPC with extra failure modes. Dual-write DB and queue without an outbox (plate 224). Retrying a non-idempotent consumer (plate 225).
