DatabaseIndex Only Scan

INCLUDE makes an index covering without extra sort keys.

A covering index contains every column the query needs → Index Only Scan (visibility map permitting). Extra columns in the key affect sort and uniqueness. INCLUDE (Postgres 11+) stores them in the leaf only. SELECT id, email WHERE email=? → INDEX (email) INCLUDE (id).

Both columns in the key

INDEX(email, id)

unique / order on email then id fanout pays for id in every internal node WHERE email = ? still works WHERE id = ? does not (plate 97)

Use two key columns when you ORDER BY or constrain both.

vs

Lookup key + leaf payload

INCLUDE (id)

INDEX (email) INCLUDE (id) seek on email id in the leaf no heap fetch Index Only Scan if VM bit is set

Heap fetches if the visibility map bit is not set — you still need VACUUM (plate 341).

What

Leaf payload vs key. Covering avoids heap I/O. INCLUDE does not change uniqueness or sort order.

Why

Hot read paths. EXPLAIN should say Index Only Scan, not Index Scan plus a heap fetch per row (plate 339).

Trap

Including a 2 KiB text column (fat leaves, fanout dies — plate 337). Expecting Index Only Scan on a never-vacuumed table: VM bits stay off.
