SystemvCPU · replicas · LB

Bigger machine, or more machines?

Vertical: one VM, more vCPU/RAM (4 → 16 vCPU, 16 → 64 GiB). Ceiling is the instance class; one AZ failure is 100% down. Horizontal: N stateless replicas behind a load balancer (plate 35), session in Redis, files in object storage. Capacity ≈ N × replica until the writer database is the limit (plate 37).

Scale up · one process

4 → 16 vCPU

m6i.xlarge 4 vCPU 16 GiB m6i.4xlarge 16 vCPU 64 GiB one IP, one disk, one crash Postgres primary often this first (one writer)
Simple. Shared-memory, local disk, no LB.
Hard ceiling. Failover is a different box.

Scale out · N copies

LB × N

ALB → app app app app each 4 vCPU / 16 GiB GET /health → 200 session in Redis, not RAM uploads in S3, not /tmp cron on one replica
Any replica can take the next request.
Sticky sessions = fake scale-out.
What

Up = bigger process. Out = more processes + a shared store. App servers scale out; a single primary still scales up until you replica-read or shard.

Why

Copies add capacity and survive one crash — if the session was not only on the dead box. Interviews: stateless means where the session lives.

Trap

Horizontal with sessions in local memory (user hits box 2, empty session). Uploads in /tmp. Cron on every replica → 4 emails. Pool max × N > max_connections (plate 03).
