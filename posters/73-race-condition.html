BackendLost update · qty 1→0 twice

Two writers. No referee.

A race is concurrent access to shared mutable state, at least one write, no happens-before. Two checkouts both read qty = 1 and both write 0: two shipments, stock 0 — a lost update. In C++ a data race is undefined behavior. In Java/Go the program is defined and still wrong. Fix: mutex (plate 74), atomic RMW, or one owner thread.

Read-modify-write, interleaved

Lost update

qty = 1 T1 load qty → 1 T2 load qty → 1 T1 store 0 sold T2 store 0 sold again want: 1 sale, qty 0 got: 2 sales, qty 0

Check-then-act (if (qty > 0)) is the same window with a branch.

fix

Happens-before

One writer at a time

mu.lock() if qty == 0: refuse qty -= 1 // 1 → 0 mu.unlock() // T2 runs after: qty==0, refuse atomic.AddInt64(&qty, -1) // or one thread that owns qty

Mutex for an invariant. Atomic for a single integer. Queue if you can avoid sharing.

What

The critical section is the lines that must not interleave. Symptom: lost update, double insert, torn struct. Cousin in SQL: missing WHERE version (plate 76) or SELECT FOR UPDATE.

Why

Interviews: point at the window between load and store, then pick a referee (plate 74) — or don’t share (plate 75).

Trap

“It works on one core.” Preemption still splits the two lines; many cores just make it common. Tests that never interleave. A sleep that “proves” the bug is not a fix.
