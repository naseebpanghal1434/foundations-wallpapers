SystemZADD · rank · window

A leaderboard is a sorted set.

Top 100 is a Redis sorted set, not ORDER BY score DESC per view. ZADD lb:global 1840 ada is O(log n). ZREVRANGE 0 99 WITHSCORES is the page. ZREVRANK is one user’s rank. Daily board = lb:2026-08-26.

Sort at read

ORDER BY

SELECT * FROM users ORDER BY score DESC LIMIT 100 -- every profile hit ties scramble n log n on the request 1e8 rows: table scan

Fine for a cold weekly recap. Fatal as the live play path. Cron-every-5-min is the same design with a delay.

vs

Ordered index

ZSET

ZADD lb:global 1840 ada ZREVRANGE 0 99 WITHSCORES ZREVRANK lb:global ada key = lb:2026-08-26 tie = (score, userId) prune below top-k

Stable ties: score then userId. Millions of users: shard by game. Do not one-key 1e8 members.

What

Ordered index, not a sort at read. Time windows are extra keys. Writes update the set; the profile row can lag. Top-k only? Drop members below the cutoff.

Why

Game / sales leaderboard. They want O(log n) update + O(k) range, not a table scan.

Trap

Sorting n users in the API. One giant ZSET of the whole company forever. Unstable ties. Cron recompute every 5 minutes as the only live path.
