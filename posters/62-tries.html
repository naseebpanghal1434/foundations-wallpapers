DSAAutocomplete

A trie is a prefix tree.

Each edge is a character. A word is a path; a flag on the last node says “this path is a complete word.” Search and insert cost O(length of the word), not O(dictionary size). Autocomplete: walk the prefix, then collect the subtree. That is why it exists.

Shared prefixes · walk letters

Trie

c a / \ r t / t car cat cart "ca" → node a → {car, cart, cat} O(len + hits)

Kids: array[26] or a hashmap. end bit (or count) on the node. Delete is “clear the bit, prune dead branches.”

vs

Exact words only

Hash set

{"car","cat","cart"} has "cat"? O(1) avg starts with "ca"? scan every word O(n · len)

Perfect for exact membership. Prefix, “typeahead,” word-break dictionary walk — you wanted a trie (or all prefixes stored, which is a worse trie).

What

Prefix tree. Time follows the string, not how many strings you already stored. A BST of words is O(len · log n) and still clumsy at “all keys with this prefix.” Tries also power IP routing and a cheap startsWith.

Why

Search-box interviews: “design autocomplete.” Walk the query, DFS/BFS the remaining nodes, rank if you stored counts. That is O(length of what’s typed + size of the answer).

Trap

A HashSet when you need prefixes: words.filter(w => w.startsWith(q)) on a million words. Also a trie for exact lookup only (a hash set is simpler). Forgetting the end flag: car then makes you think ca is a word.
