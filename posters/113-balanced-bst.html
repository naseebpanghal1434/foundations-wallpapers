DSAAVL · rotations

Height must stay log n.

A balanced BST rewrites the tree on insert/delete so height stays Θ(log n). AVL: each node keeps |hL − hR| ≤ 1, then rotates. Red-black: color invariants, same big-O, fewer rotations. TreeMap / std::map are this, not a hashmap.

No balance · a stickInsert 1, 2, 3: 1 → 2 → 3, height 3. Search is linear. Sorted inserts into a raw BST are how you accidentally build a list.

Right-right · rotate leftAVL insert 3 into 1-2 is RR on 1. Left-rotate(1) → 2 / \ 1 3. Inorder still 1,2,3 — still a BST. Every node keeps |hL − hR| ≤ 1.

3

Four casesLL: right-rotate node. RR: left-rotate node. LR: left-rotate the child, then right-rotate the node. RL is the mirror. Local pointer surgery restores height.

LL LR RR RL
What

Search/insert/delete O(log n) worst-case. Rotation is local pointer surgery that preserves inorder (so it stays a BST) and restores height. AVL is strict; red-black is looser, same class.

Why

Why TreeMap beats a HashMap when you need ordered keys, range, floor/ceiling. Why a hashmap is still faster for pure lookup. Interviews: “how does a balanced tree stay log n?” Rotations.

Trap

Calling HashMap balanced. Implementing AVL in a screen — they usually want the idea and a rotation diagram, not 80 lines. Also: heap is balanced-as-complete, but not a search tree (plate 58, 114).
