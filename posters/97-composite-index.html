DatabaseLeftmost prefix

INDEX(a, b) is not INDEX(b).

A B-tree on (a, b) is sorted by a, then b. It can jump on a, or on a then b. It cannot start in the middle. WHERE b = 1 does not use that index (classic rule). Put equality columns left, range columns next. If the index holds every column the query needs, you can skip the heap — a covering index.

INDEX (user_id, created_at)

Prefix hits

WHERE user_id = 7 WHERE user_id = 7 AND created_at > $t ORDER BY user_id, created_at covering: SELECT created_at WHERE user_id = 7 -- heap not required

Leftmost prefix. Equality on the left, range on the next. INCLUDE extra columns in Postgres to cover without changing sort.

vs

Same index, wrong query

No prefix

WHERE created_at > $t WHERE status = 'open' -- leading column unused WHERE user_id > 7 AND created_at = $t -- range on a: b is a filter, -- not a seek

You wanted INDEX(created_at) or (status, created_at). Extra storage (plate 02) that the planner is allowed to ignore.

What

(a,b,c) serves a / a+b / a+b+c. Covering = index-only scan (visibility map in Postgres, plate 96). Match ORDER BY to the index to skip a sort. LIKE 'foo%' can use a btree; LIKE '%foo' cannot.

Why

Most real WHERE clauses are two columns. One composite beats two single-column indexes for that query. Interviews: write the index in column order, then say what it cannot do.

Trap

INDEX(a,b) for WHERE b = 1. Boolean or low-selectivity leading column. A covering index you never SELECT from. Three overlapping composites that all slow every write.
