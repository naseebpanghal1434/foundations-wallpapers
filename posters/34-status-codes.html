BackendRFC 9110 · 2xx 4xx 5xx

Status codes are a contract.

The number tells the client what to do next. 2xx succeeded. 4xx the client must change the request. 5xx the client may retry. Returning 200 with { "error": true } hides that contract from browsers, caches, load balancers, and on-call.

done

200 201 204

200 OK. 201 Created + Location. 204 no body. 304 cache still valid (not a 2xx, no body).

your request

401 ≠ 403

401 who are you. 403 we know you, no. 400 bad input. 404 missing. 409 conflict. 429 slow down.

our fault

500 502 503

500 bug. 502 bad gateway (upstream died). 503 unavailable. 504 gateway timeout. Retry 502/503/504, not 400.

the rule

4 vs 5

User can fix the request → 4xx. Try later → 5xx. 301/308 preserve vs change method. 429 is a limit, not a crash.

What

RFC 9110. 404 on a missing id, 400 on a malformed id. 409 when the version doesn’t match (optimistic lock). 429 + Retry-After. 401 ≠ 403 (plate 14).

Why

Load balancers, caches, and retry libraries key off the number. A 200-error means they cache a failure and never retry a blip.

Trap

200 for everything. 500 for validation errors (blames you, retries forever). 404 for “not allowed” (hides existence — sometimes intentional). 301 vs 302 if you care about method preservation.
