DatabaseEstimated vs actual

EXPLAIN is a guess. ANALYZE ran it.

EXPLAIN prints the plan the planner likes: Seq Scan vs Index Scan, estimated cost, estimated rows. EXPLAIN ANALYZE executes the query and writes actual time and actual rows next to the guess. The bug is usually “estimated 500,000, actual 12” — stale stats, wrong join order, an index you thought it used.

Planner’s story

EXPLAIN

Seq Scan on orders cost=0.00..18432.00 rows=500000 Filter: user_id = 7 -- never ran -- never timed -- never counted

Looks cheap on a small table, looks obligatory on a big one. You have not measured.

vs

What the engine did

ANALYZE

Index Scan using orders_user_id actual time=0.04..0.18 rows=12 loops=1 Buffers: shared hit=4 Seq Scan would have been actual time=812ms rows=12 ← guess was 5e5

Read Seq vs Index, then estimated vs actual rows. Off by 10× → ANALYZE the table, check the index (plate 97).

What

EXPLAIN (ANALYZE, BUFFERS) in Postgres. Seq Scan = walk the heap. Index Scan = seek + heap. Index Only Scan = covering + visibility map. Nested Loop / Hash / Merge are join algorithms. Look at the node whose actual time dominates.

Why

You cannot tune what you have not seen. Interviews: paste a plan, point at Seq Scan vs Index, notice row estimates, say “stats or the wrong composite.”

Trap

EXPLAIN without ANALYZE — you believed a guess. EXPLAIN ANALYZE on a DELETE in prod (it runs). Seq Scan is not always a bug (tiny table). Ignoring “rows=1 vs actual=1e6” on the inner side of a nested loop.
