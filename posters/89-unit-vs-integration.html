Backendfake repo vs Testcontainers

Mocks are not the database.

A unit test fakes I/O and checks rules: placeOrder({ qty: 2 }, fakeRepo) → total === 80. An integration test uses real seams: Testcontainers Postgres, real migrations, unique constraints, POST /orders → 201 and a row. expect(db.query).toHaveBeenCalledWith("SELECT …") proves you typed the string, not that Postgres accepts it.

Fake the neighbors

Unit

placeOrder({ qty: 2 }, fakeRepo) expect(total).toBe(80) fast · no Docker proves the rule, not SQL

Mocks at the IO boundary (plate 88 repo). Hundreds on every PR (plate 90). If the fake repo is wrong, the test is still green.

vs

Real pieces, still in CI

Integration

POST /orders { qty: 2 } → testcontainers Postgres expect 201 and a row unique constraint fires migrations actually run

App + DB (or queue) for real. Catches SQL, txns (plate 07), FKs. Fewer of these. E2E is the next step: a browser against staging.

What

Pyramid: many unit, fewer integration, few E2E. Assert state and status, not only that a mock was called. Unit is allowed to lie about I/O; integration is not.

Why

Rules change often — unit tests catch that in milliseconds. Unique constraints, migrations, isolation (plate 40), and the real query plan only show up against a real DB.

Trap

Tests that only test mocks. A typo in SQL still ships. 100% coverage, zero confidence. Shared dirty DB without truncate/transactions. Mocking the unit under test.
