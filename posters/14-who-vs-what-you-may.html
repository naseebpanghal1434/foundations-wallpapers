Backend401 vs 403 · IDOR

Who you are is not what you may do.

Authentication binds a request to a principal (session, JWT sub, mTLS CN). Authorization is (principal, action, resource). HTTP: 401 = no valid credentials; 403 = credentials ok, policy denied. The names are historical; 401 is not “not allowed.”

authn · principal

401

POST /login Set-Cookie: sid=…; HttpOnly req.user = {id: 42, role: "user"} missing/invalid Cookie or Bearer → 401 WWW-Authenticate: Bearer
Password, OAuth, magic link, mTLS.
Result: this socket is user 42. Not permission.
then

authz · this row

403

DELETE /orders/88 SELECT user_id FROM orders WHERE id = 88 -- 42 ≠ owner and role ≠ admin → 403 IDOR: /orders/89 still 200 if only isAuthenticated()
Check the resource, not only “logged in.”
Hide-the-button is not a control. Clients send any URL.
What

401 = unknown. 403 = known, denied. Authz is always this user, this action, this row — not a navbar flag.

Why

The API is the enforcement point. Interviews: IDOR = change the id, get someone else’s row (OWASP A01).

Trap

isAuthenticated() on DELETE /orders/:id. Trusting req.body.userId. Returning 404 for every deny can hide existence — that’s a choice, not a substitute for the owner check.
