BackendTTL · LRU · stampede

Name the eviction before the cache.

Name eviction before SET. TTL (EX 60) for news and sessions; LRU (plate 150) for bounded RAM; miss fill under a lock (SET NX EX 10 / singleflight) or a stampede melts the DB (plate 94). Cache-aside: miss → DB → SET. Write-behind can lose writes.

Time

TTL

SET k v EX 60 news, sessions jitter the 60s or they die together

Safety net. Not a strategy by itself (plate 8). Aligned TTLs are a stampede.

RAM

LRU

hot keys stay cold keys leave maxmemory-policy allkeys-lru

Name the victim. Hash + list (plate 150). Include id in the key.

Miss

One fill

SET lock:k NX EX 10 winner → one SELECT waiters share or serve stale

No lock on miss = stampede (plate 94). Null-cache 404s.

Cache-aside: miss → DB → SET. Write-through: DB and cache together. Write-behind: cache then async DB — faster, not durable. Version the key on deploy.

What

Policy first: what is stale, what is evicted, who fills. Key includes the resource id and a schema version. Lock or singleflight on miss.

Why

“Design a cache” or any read-heavy system. Interviewers want stampede + eviction, not “we’ll add Redis.”

Trap

Infinite TTL. Caching a user object without the id in the key (cross-user leak). No lock on miss. Write-behind as if it were WAL.
