Databasefanout ~100 · height 3–4

A B+ tree is wide and short. Leaves hold rows.

A B+ node is a page (8 KiB in Postgres). Fanout is ~100–300 keys, so 1e9 rows sit at height 3–4. Internals are keys + child pointers; payloads live in linked leaves — a range scan walks the chain, not the tree. Postgres btree is this shape (plate 2).

RAM textbook

Binary

1e9 rows 2-way node height ≈ 30 30 hops if each hop is a page that is 30 I/Os

Fine in RAM. On disk, a 2-child node wastes the 8 KiB page.

vs

One page, hundreds of keys

B+

8 KiB node fanout ~100 height 3–4 point: height I/Os range: leaf → leaf Postgres btree

Leaf value is a TID (or the row, if clustered). uuid4 keys randomize splits (plate 348).

What

Disk-friendly search tree. Point lookup = height I/Os. Range = height + leaf chain. Key size sets fanout: smaller keys, shorter tree.

Why

Indexes are not binary trees from a RAM textbook. An 8-byte key packs ~100–300 siblings; a fat key does not.

Trap

A 2 KiB JSON key in the index — fanout collapses, height grows, cache dies. Then every lookup is more pages.
