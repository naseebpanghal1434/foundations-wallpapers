DatabaseHow COMMIT survives a crash

Log first. Then the pages.

Durability (plate 41, the D) is not “the table file is up to date.” It is: append the change to a log, fsync that log, then you may say COMMIT. Heap pages flush later. Crash? Replay the log from the last checkpoint. Sequential log first; random pages when you can afford them.

Write the table, hope

No WAL

update heap page 4 update heap page 9 crash page 4 new, page 9 old half a transaction on disk

Random writes, no single “this COMMIT happened” record. Power cord pull fails the D.

vs

Append, fsync, then data

WAL

1 append records to WAL 2 fsync WAL 3 COMMIT returns 4 dirty pages later (checkpoint) crash → redo from last checkpoint

Postgres WAL, InnoDB redo, SQLite WAL. Group commit batches many txns into one fsync.

What

Write-ahead: the log is the source of truth for recovery. Checkpoint = “heap is caught up to here, older log can go.” Replication often ships the same log (Postgres). Atomicity (plate 07) is a rollback; D is the fsync.

Why

Disks lie until you force them. Interviews: draw COMMIT as log+fsync, not as “UPDATE returned.” This is why a commit can be 1ms of WAL and not 1ms of rewriting a 8KB page ten times.

Trap

fsync=off / synchronous_commit=off — COMMIT returns, a crash eats it. That is speed, not D. Unlogged tables skip WAL on purpose. Putting WAL on a disk that ignores flush. Confusing checkpoint with COMMIT.
