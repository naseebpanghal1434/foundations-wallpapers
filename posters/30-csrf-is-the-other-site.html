BackendSameSite=Lax · Origin

CSRF is the other site.

Cross-Site Request Forgery: another origin triggers a request the browser authenticates with your cookies. evil.com can POST a form to https://bank.com/transfer; the browser attaches Cookie: sid=…. CORS does not stop this — a simple form POST has no preflight.

evil.com · you are logged in

The write

<form action="https://bank.com/transfer" method="POST"> <input name="to" value="attacker"> <input name="amt" value="1000"> </form> <script>form.submit()</script>

Cookie rides along. SameSite=Lax (Chrome default since 80) blocks this cross-site POST.

vs

Cookie ≠ proof of intent

SameSite + token

Set-Cookie: sid=…; Secure; SameSite=Lax CSRF: hidden field ≠ cookie check Origin / Referer Authorization: Bearer … (not sent by a form)

Lax stops the naive form. A synchronizer token (or header-only session) stops the rest.

What

Forged write using cookie credentials. XSS steals the secret; CSRF uses it in place. SameSite=None requires Secure. Check Origin on state-changing POST.

Why

Cookie sessions. Interviews pair this with CORS (plate 15): CORS hides JS reads; CSRF is a write the browser already knows how to send.

Trap

Thinking CORS prevents CSRF. SameSite=None; Secure on a session cookie “for the mobile app.” JSON APIs that still accept application/x-www-form-urlencoded POST. State-changing GET.
