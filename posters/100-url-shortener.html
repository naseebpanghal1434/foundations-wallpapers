SystemBase62 · 301 vs 302

A short URL is a lookup.

You are not compressing the long URL. You mint a unique slug, store slug → url, and redirect. Encode a numeric id in base62 (0-9a-zA-Z): 7 characters is ~3.5e12 keys. Cache the mapping. Then pick 301 or 302 — 301 is cached by browsers forever, so you lose the click and cannot change the destination.

Sequential ids enumerate every private link. 301 is a one-way door (plate 34).

vs

Mint, store, 302

Base62

id = snowflake (plate 93) slug = base62(id) bH6kQ3 or custom alias UNIQUE (slug) SET slug → url cache GET /bH6kQ3 302 Location: https://… (307 keeps the method)

302/307 if you want counts, expiry, or to change the target. Cache GET. Unique slug is a constraint, not a hope.

What

Write: generate id → encode → insert with unique slug (custom aliases collide). Read: cache, then DB, then redirect. Rate-limit minting (plate 33). Viral slug is a hot key (plate 94) — the cache is the design, not an extra.

Why

This is the default “design a shortener” interview. They want: keyspace math, uniqueness, redirect semantics, cache, not a regex that shrinks the string.

Trap

Sequential guessable ids. 301 because “the URL moved permanently” — true, and now CDNs and Chrome own the mapping. Hashing the long URL without collision handling. No unique index on slug. Putting the destination only in Redis.
