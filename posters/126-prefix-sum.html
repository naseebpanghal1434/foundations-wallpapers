DSApsum[r] − psum[l-1]

A range is two prefix lookups.

prefix[i] = a[0]+…+a[i]. Sum of [l,r] = prefix[r] − prefix[l−1] (or prefix[r+1]−prefix[l] with a leading 0). Build O(n), each query O(1). Subarray sum equals k: walking r, look up how many prefixes equal prefix[r]−k — a hashmap of prefix counts.

Leading 0 · two lookups

Range sum

a = [2, 3, 1, 4] p = [0, 2, 5, 6, 10] sum[l,r] = p[r+1] - p[l] sum[1,3] = 10 - 2 = 8 # 3+1+4 # no leading 0: # sum[l,r] = p[r] - p[l-1]

2D: S[r][c] is the rectangle (0,0)→(r,c). Query four corners (inclusion-exclusion). XOR is the same cancel-twice trick.

k

How many prefixes = psum − k

Sum = k

k=4 map {0: 1} psum 0,2,5,6,10 at 6 need 2 — seen [1,2] = 3+1 at 10 need 6 — seen [3,3] = 4 lookup, then map[psum]++

Count prefixes, not one index. Initial {0:1} is the empty prefix. Insert after the lookup — k=0 would self-hit.

What

Precompute running totals on an immutable array. sum[l,r] = prefix[r] − prefix[l−1] (guard l=0) or the leading-0 form. Updates need Fenwick / segment (plates 120–121). Same machine for prefix XOR.

Why

Range sum, range average, pivot index, subarray sum k, count of subarrays with sum k, 2D region sum. Many range sums and no updates: this, not a nested loop. The hashmap move is plate 109 on prefixes.

Trap

Off-by-one on the leading 0: prefix[r]−prefix[l] drops a[l] if l was inclusive. Hashmap that stores one index, not a count — misses duplicates and k=0. Mutating a after the build.
