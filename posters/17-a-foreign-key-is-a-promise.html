DatabaseREFERENCES · 23503

A foreign key is a promise.

PRIMARY KEY (id) is UNIQUE NOT NULL — one row identity. FOREIGN KEY (user_id) REFERENCES users(id) is a constraint: INSERT/UPDATE of user_id must match an existing users.id, else SQLSTATE 23503. ON DELETE RESTRICT | CASCADE | SET NULL is the delete policy.

CREATE TABLE users ( id bigint PRIMARY KEY, email text UNIQUE NOT NULL ); -- btree on id, btree on email

This row, and only this row, is 7. Referenced side must be UNIQUE/PK.

FK

orders.user_id must exist

23503

ALTER TABLE orders ADD FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE RESTRICT; INSERT … user_id=99; -- 23503 DELETE FROM users WHERE id=7; -- fail if orders

Index orders(user_id) or deletes/joins seq-scan the child. CASCADE wipes children.

What

Referential integrity in the catalog. App if statements are not a substitute. The C in ACID at commit (plate 41).

Why

Without the FK, user_id = 99 commits and JOINs drop the row. Interviews: name 23503 and ON DELETE.

Trap

Skipping FKs “for flexibility.” ORM races, migrations, and raw SQL will write orphans. ON DELETE CASCADE on a user delete you thought was soft. No index on the referencing column.
