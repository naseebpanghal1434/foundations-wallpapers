LangC · not Java

volatile is for MMIO, not mutexes.

C volatile: every access hits memory; the compiler will not reorder those accesses versus other volatiles — for device registers that change without the compiler knowing. It is not atomic and not a barrier for other threads. Java volatile is a different word (visibility ≈ acquire/release).

Wrong · not a lock

Spin on it

volatile int flag; while (!flag) {} // not hoisted — still // not atomic // no acquire // ARM may never see // the other core's 1 plain bool: same bug

Threading needs atomic_int / std::atomic / a mutex (plate 74, 330). MSVC has extra flags; they are still not a mutex.

vs

Device register · one location

MMIO

*(volatile uint32_t*) 0x40001000 = 1; each store must hit the register, not a cached copy in a GPR atomic_int flag; flag.store(1, release);

The compiler must not coalesce MMIO writes. That is the job. Coherence with another CPU is not.

What

Compiler I/O to a location. No atomicity, no inter-thread happens-before. Java volatile is the JMM visibility keyword — do not port the word to C.

Why

Drivers, embedded, memory-mapped status registers. The #1 C concurrency misconception in interviews.

Trap

Porting Java volatile to C. Signaling a thread with a plain bool on ARM. Using volatile to “keep the compiler from optimizing” locals in a hot loop — that forces RAM (plate 312).
