BackendGET /orders/12 vs POST /graphql

Resources, or a query.

REST names resources and uses HTTP verbs: GET /orders/12 is cacheable, status codes fall out of HTTP (plate 34). GraphQL names a graph: one POST /graphql, a schema, the client picks fields. REST over-fetches or under-fetches (N round trips). GraphQL still runs resolvers — N+1 SQL is plate 10. DataLoader / joins still matter.

Nouns + verbs

REST

GET /users/1 GET /users/1/orders GET /orders/88/items GET /items/2 … a screen, 12 trips

Cacheable GETs. CDN and rate limits understand the URL. Under-fetch → more RTTs. Over-fetch → fat payloads. A BFF / /api/home is the REST answer to chattiness.

vs

One POST, a schema

GraphQL

query { user(id: 1) { name orders { items { sku } } } }

One round trip. Authz is per field, not per URL. Caching and HTTP codes get harder. Mutations still need an idempotency key (plate 29).

What

REST: many endpoints, HTTP semantics. GraphQL: one endpoint, typed schema, queries and mutations. It does not magically become one SQL query.

Why

Mobile on a slow radio hates 12 round trips. Public APIs and CDNs like REST. Interviews: draw both, name over/under-fetch, say where authz lives.

Trap

GraphQL as an unauthenticated database: user(id:) returns anyone, introspection on in prod, no query depth/cost limit. REST that needs 12 round trips for one screen.
