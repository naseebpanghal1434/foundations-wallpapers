BackendRFC 9110 · Idempotency-Key

Idempotent means do it twice.

Idempotent: 1 request or n retries leave the same stored result. RFC 9110: GET, PUT, DELETE, HEAD, OPTIONS are; POST is not. Timeouts and LB retries replay the bytes. POST /charges without Idempotency-Key inserts a second row.

Timeout · client retries

POST /charges

1. POST → INSERT charge $30 200 lost on the wire 2. POST → INSERT charge $30 total $60 two rows

The first COMMIT likely landed. A retry without a key is a new INSERT.

vs

Same key + same body

Idempotency-Key

Idempotency-Key: 7f3a-… UNIQUE (user_id, key) 1. POST → 201 charge_id=88 2. POST → 200 same 88 same key, other body → 409

Store key → status + body (TTL 24h, Stripe-style). The UNIQUE insert is the mutex.

What

HTTP’s contract is per method. You make POST idempotent with a client-generated key persisted under a unique constraint, scoped per user. Replay returns the stored response, not a second side effect.

Why

Networks drop the 200. Users double-click Pay. LBs retry (plate 19). Payments, tickets, “send email” must survive that. Interviews: retries plus money.

Trap

Key only in RAM (restart forgets). First call charged then returned 500 — retry must return charge 88, not insert 89. GET /delete?id=1 is a side effect pretending to be safe.
