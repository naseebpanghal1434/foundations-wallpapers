DatabaseUPDATE … WHERE version · 409

Write if the version still matches.

Don’t hold a row lock while the user thinks. Read the row and its version. Write with UPDATE … WHERE id = $1 AND version = $old. rowcount = 0 means someone else committed — HTTP 409, re-read, retry. HTTP twin: If-Match / ETag. Missing the WHERE is plate 73’s lost update, in SQL.

Hold the row the whole time

Pessimistic

BEGIN; SELECT qty FROM items WHERE id=7 FOR UPDATE; -- user confirms… -- Stripe… seconds UPDATE items SET qty=11; COMMIT;

Fine for a 2 ms txn. Blocks every other writer of row 7. Don’t wait on the network while you hold it.

or

Compare-and-swap the row

Optimistic

SELECT qty, version FROM items WHERE id=7; -- qty=12 version=4 UPDATE items SET qty=11, version=5 WHERE id=7 AND version=4; -- 0 rows → 409 Conflict -- re-read, re-apply, retry

The WHERE is the lock. Cap retries. updated_at works if you treat it as opaque.

What

A version int on the row. Commit only if it still equals what you read. Retry is: read again, re-apply the business rule, UPDATE again — not “return 409 and stop.”

Why

Editors, carts, inventory — overlapping writes with think-time. Pessimistic serializes them; optimistic lets them overlap and pays a retry on true conflict.

Trap

409 with no re-read. Bumping version in the SET but leaving it out of the WHERE — you never notice the collision. Holding FOR UPDATE across Stripe.
