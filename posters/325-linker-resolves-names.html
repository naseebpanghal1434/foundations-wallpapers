Langld · .o · undefined ref

The linker resolves names to addresses.

cc -c produces a .o with reloc holes: call printf is still “undefined.” ld (or lld, link.exe) concatenates .o/.a, assigns addresses, patches relocs, emits the executable or .so. Dynamic linking delays some of that resolution to load (PLT/GOT).

1

Compile unitscc -c a.c → a.o. Symbols and relocations, not a runnable address.

.o
2

Archive is a pile of .oar rcs libfoo.a *.o. The linker pulls members that satisfy undefined names.

.a
3

Name → address, or a linker errorUndefined foo is ld, not cc — not a runtime NameError unless the .so is dynamic.

ld

--as-needed drops unused .so. LTO is optimize at this step. Circular .a may need --start-group.

What

Name → address after compile. Static: everything in the binary. Dynamic: libfoo.so at load, PLT/GOT (plate 371). The ABI says which register is arg0 when those calls happen (plate 326).

Why

“Undefined reference to foo” is the linker. Order of .a on the command line still matters for a single-pass ld.

Trap

Assuming a header “links” the library — it only declares. Circular .a without --start-group. Mixing libc++ and libstdc++ in one image.
