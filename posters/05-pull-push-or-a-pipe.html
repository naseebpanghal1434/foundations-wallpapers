NetworkHTTP · SSE · WebSocket

Pull, push, or a pipe.

Three transports, same origin. HTTP: one request, one status, done (keepalive may reuse the socket, plate 277). SSE: GET with Content-Type: text/event-stream, server writes data: lines. WebSocket: Upgrade: websocket → 101, then RFC 6455 frames both ways.

Request / response

HTTP

GET /orders/12 200 {"total":80} Cache-Control, ETag one body, then end
Status codes. Cacheable GETs.
H1: one at a time per fd. H2: streams.

REST, fetch, forms.

Server → client stream

SSE

GET /stream 200 text/event-stream data: token id: 42 : comment / keepalive
Unidirectional. EventSource retries + Last-Event-ID.
GET only. Disable proxy buffer (X-Accel-Buffering: no).

LLM tokens, ticks, feeds.

Bidirectional frames

WebSocket

GET /chat Upgrade: websocket 101 Switching Protocols opcode 1 text / 2 binary 9 ping · 10 pong · 8 close
You own heartbeats, reconnect, backpressure.
H2: CONNECT + :protocol, not a 101.

Chat, collab, games.

What

HTTP = request/response. SSE = still HTTP, one direction. WebSocket = 101 then a framed socket. gRPC streaming is HTTP/2 (plate 282).

Why

Fetch a resource with HTTP. Stream tokens with SSE. Chat when both sides send anytime.

Trap

Opening a WebSocket to do one GET — you then own ping/pong and reconnect. SSE cannot POST a body. Proxies buffering SSE into one dump at close.
