DatabaseRANGE · LIST · HASH

Partitioning is routing, not a free index.

Declarative partition: parent table, children by RANGE/LIST/HASH of a key. The planner prunes children if WHERE contains that key. It does not replace an index inside a partition. Attach/detach is why time-series drops old data in O(1) metadata.

Key is in the WHERE

Prune

events RANGE (ts) events_2026_08 events_2026_09 WHERE ts >= '2026-08-01' AND ts < '2026-09-01' → one child DETACH + DROP = O(1) retain

PK/unique must include the partition key. Index each child as if it were the table.

vs

Filter on the other column

All children

WHERE user_id = 7 on a ts-range parent planner cannot prune opens every month planning time ∝ partition count

You still need INDEX (user_id) on each child — or also filter ts.

What

Constraint-based routing of rows to files. Pruning needs the key in the query. HASH is for shard-by-tenant, not for time drop.

Why

Retention, huge time-series, tenant isolation. Dropping a month is detach, not DELETE 1e9 rows.

Trap

Thousands of partitions and no prune (planning time explodes). Unique on (id) without the partition key — Postgres will refuse it.
