DatabaseSnapshots, not read locks

Readers don't block writers.

MVCC keeps versions. A reader pins a snapshot and sees the row as of that snapshot. A writer makes a new version instead of overwriting in place. They don’t wait on each other. Isolation (plate 40) is “which versions you are allowed to see.” Vacuum is how dead versions leave.

Writers still block writers on the same row. MVCC is not “no locks.”

What

Postgres: UPDATE/DELETE leave a dead tuple; autovacuum (VACUUM) reclaims it and updates the visibility map (index-only scans, plate 97). InnoDB: undo log + purge. Snapshot = the set of transactions whose writes you see.

Why

OLTP wants readers and writers at once. This is why a long report doesn’t have to freeze checkout — until the report is so long it prevents vacuum. Interviews: snapshot, no reader/writer block, vacuum, bloat.

Trap

Long transactions bloat. idle in transaction pins xmin; dead tuples cannot go; tables and indexes swell; wraparound is the late stage. A connection-pool leak is a vacuum problem. Also: “MVCC means I skip FOR UPDATE” — lost updates still happen (plate 40).
