DatabasePQexecParams · bind

A prepared statement parses once. $1 is data.

SQL injection (plate 16) is the parser seeing user bytes as syntax. A prepared statement parses SELECT … WHERE id=$1 once, then binds a typed value that never enters the parser as text. ORMs that interpolate strings are not prepared.

user bytes in the SQL string

Glued

"… WHERE name='" + user + "'" user = ' OR 1=1 -- → WHERE name='' OR 1=1 --' parser compiles attacker SQL

Python format('… %s …', user) is the same bug. Escaping quotes by hand will miss an encoding.

vs

Parse once · bind typed

$1

PQexecParams( "… WHERE name=$1", varchar, user) Parse / Bind / Execute psycopg2 %s · JDBC ? PREPARE then EXECUTE

Identifiers (table, column names) cannot be bound — allowlist those. Plan reuse is a bonus.

What

Protocol-level bind. Types on the wire. The value cannot close the quote because it never enters the parser as text.

Why

The actual fix, not “escape quotes.” Plate 16 is the slogan; this is the protocol.

Trap

format('… %s …', user) in Python. Prisma/Knex raw. Binding a whole IN () list by concatenating anyway.
