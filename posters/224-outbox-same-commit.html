DatabaseDual write · poller

Write the outbox in the same commit.

Dual write (COMMIT order, then Kafka.send) can lose or phantom the event. Outbox: INSERT order and INSERT outbox in one COMMIT — that COMMIT is WAL (plate 95). A poller SELECT … FOR UPDATE SKIP LOCKED publishes, then marks sent.

Two writes, two fates

Dual write

COMMIT order crash → Kafka never lost event publish, then crash before COMMIT phantom order

If you say “we’ll publish after commit,” they kill the process in the next sentence. The bus is not in the WAL.

vs

One transaction · WAL

Outbox

BEGIN INSERT orders INSERT outbox COMMIT -- fsync WAL poller: SELECT … FOR UPDATE SKIP LOCKED publish; mark sent

The row and the event share one fsync. CDC / Debezium is the same idea; event order is commit order. Delete or archive after ack.

What

The database COMMIT is the atomic boundary. The bus is downstream replay, like crash recovery from WAL. Outbox rows are the durable queue.

Why

The dual-write question. Same-commit outbox (or CDC) is how the event cannot diverge from the row.

Trap

Publish then commit. Commit then publish without an outbox. Poller without SKIP LOCKED so two publishers double-send. Giant outbox never cleaned.
