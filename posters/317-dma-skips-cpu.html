Archbus · IRQ after

DMA moves bytes without the CPU.

Direct Memory Access: the device writes/reads RAM via the memory controller. CPU sets up a descriptor (addr, len), device transfers, IRQ when done (plate 298). Zero-copy NICs and NVMe work this way. CPU memcpy of 1 GiB wastes cores and cache.

1

Driver maps the bufferIOMMU is the I/O TLB. Bounce buffers if the device cannot reach high mem.

IOMMU
2

Kick the doorbellCPU programs addr, len. Then it should do other work — not memcpy.

kick
3

Device DMAs into RAMBytes move on the bus. Cache coherence with DMA is a driver problem (snoop or flush).

copy
4

IRQ, then NAPI / completionUserspace sees a finished syscall, not the bus. NVMe ~100 µs includes this path.

IRQ
What

The CPU programs; the device copies. Buffer must be DMA-capable: aligned, pinned.

Why

10–100 GbE, NVMe queues. Kernel bypass (DPDK) still uses DMA, just from userspace.

Trap

memcpy the packet in the app after the NIC already DMAed it into a buffer you could have parsed. Unaligned, unpinned buffers.
