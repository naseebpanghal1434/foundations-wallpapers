SystemInverted index · rank

Search is tokens pointing at docs.

Full-text is an inverted index: token → posting list of doc ids. Analyze: lowercase, stem, drop stopwords. Query: intersect lists, rank BM25. Not LIKE '%red shoe%' on 50M rows. Page with search_after, not OFFSET. Typeahead is plate 206; this is documents.

50M rows · seq scan

LIKE

SELECT * FROM docs WHERE body LIKE '%red shoe%' no token list no BM25 OFFSET 10000 still walks every row

A leading wildcard cannot use the B-tree (plate 2). ILIKE is the same scan. Reindex is not UPDATE in place.

vs

token → postings

Invert

doc 9 red running shoe → red, run, shoe shoe: 9, 17, 80 red: 9, 22 intersect, then BM25 search_after (score,id)

Elasticsearch / Lucene is this. The DB is source of truth; the index is a derived view (lag is OK if you say it). Filters are bitsets / doc values.

What

Analyze → invert → query → rank → page. Updates are reindex. Pagination is search_after, not OFFSET 10000.

Why

Design search. They want inverted index + BM25, not Postgres ILIKE. Mention lag and that the cluster is not the system of record.

Trap

LIKE '%term%'. Reindexing on every keystroke of a doc. OFFSET 10000 on a ranked list. Treating the search cluster as the source of truth.
