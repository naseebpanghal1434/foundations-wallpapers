DatabaseGIN · ->>

jsonb is binary and indexable. json is text.

json is stored as input text. jsonb is decomposed; whitespace gone; keys unique; GIN indexes path/value. -> returns json; ->> returns text. Prefer jsonb unless you must byte-preserve. Still not a substitute for columns you filter every time.

Input text, no structure

json

{" sku " : "A1"} whitespace kept keys may repeat WHERE extra::text LIKE '%A1%' seq scan on a blob

Use it when the bytes must round-trip. Do not query it.

vs

Decomposed, GIN or expression

jsonb

WHERE extra @> '{"sku":"A1"}' GIN (jsonb_path_ops) WHERE extra->>'sku' = 'A1' INDEX on (extra->>'sku') TOAST if the doc is wide

jsonb_ops is the default (keys + containment). jsonb_path_ops is smaller, @> only.

What

A typed document in a cell. Index the expressions you query. Stats on a jsonb column are weak compared to a real column.

Why

Semi-structured extras. Event payloads. Not the whole domain model.

Trap

jsonb for every field (no constraints, no stats). Updating one key rewrites the TOASTed value. json plus LIKE as a query planner.
