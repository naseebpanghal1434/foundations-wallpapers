Database1+N round trips

N+1 is a loop.

N+1 = one query for the parent set plus one query per row. 50 users → 51 round trips. At 2 ms each that is 102 ms plus parse/plan, not 2 ms. The inner SQL can be an Index Scan (0.05 ms); the count of execs is the cost.

ORM lazy association

51 trips

users = SELECT * FROM users LIMIT 50 -- 1 for u in users: posts = SELECT * FROM posts WHERE user_id = $1 -- ×50 50 × 2 ms RTT = 100 ms extra pg_stat_statements: 50 identical

Rails .posts, Django _set, GraphQL child resolvers. The query is not in your source.

vs

IN / JOIN / dataloader

2 trips

SELECT * FROM users LIMIT 50 SELECT * FROM posts WHERE user_id = ANY($1) -- $1 = {1,2,…,50} -- or one JOIN (plate 18) SELECT u.*, p.* FROM users u JOIN posts p ON p.user_id = u.id

Dataloader batches by tick. INCLUDES / select_related / prefetch do the same.

What

A query inside a loop over rows. Fix: ANY/IN, a JOIN, or a dataloader. Look at exec count, not only SQL text.

Why

A page that “looks like one fetch” takes 1–2 s. Logs show the same WHERE user_id = $1 N times (plate 98).

Trap

Indexing the inner query and keeping the loop. LIMIT 50 on users with unbounded posts. GraphQL without a dataloader. Counting ORM calls instead of TCP round trips.
