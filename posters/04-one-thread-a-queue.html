Backendlibuv · UV_THREADPOOL_SIZE=4

One thread. A queue.

Node’s JavaScript runs on one OS thread. The event loop (epoll_wait / kqueue) collects I/O; callbacks run to completion on that thread (plate 226). libuv’s default pool is 4 threads (UV_THREADPOOL_SIZE) for fs, getaddrinfo, some crypto — not for request handlers.

JS

One V8 stack. No preemption. 10 ms JSON.parse stalls every socket. bcrypt.hashSync 50–100 ms × 100 rps saturates the core.

main thread

run-to-completion
Loop

timers → poll → check. One callback at a time. await yields. A tight for does not. setTimeout(0) is the next macrotask.

event loop

offloads fs/dns
uv

4 C threads. uv_fs_*, DNS, some crypto. CPU work: worker_threads or another process. cluster = N loops, not one shared thread.

threadpool

What

Cooperative concurrency on one thread. Thousands of keep-alives are fine if handlers await. CPU occupies the only JS thread until it returns.

Why

fs.readFileSync in a request freezes every other connection on that process. Interviews: concurrency ≠ parallelism.

Trap

Saying “Node is multithreaded.” Sync bcrypt/JSON/regex on the hot path. Filling the 4-thread pool with heavy fs so DNS waits. while(true) starves poll and timers.
