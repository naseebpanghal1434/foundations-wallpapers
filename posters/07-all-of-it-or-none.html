DatabaseBEGIN · COMMIT · WAL

All of it, or none.

Atomicity: BEGIN … COMMIT is one unit. Postgres appends WAL (plate 95); COMMIT is durable after flush (synchronous_commit, ~0.1 ms NVMe, 1–10 ms HDD). Crash mid-transaction → ROLLBACK, both rows unchanged. Isolation is a different axis (plate 40).

Transfer 30 · both writes

COMMIT

BEGIN; UPDATE accounts SET bal = bal - 30 WHERE id='A'; UPDATE accounts SET bal = bal + 30 WHERE id='B'; COMMIT; -- WAL flush, ~0.1 ms NVMe
idwasnow
A10070
B1040

Outsiders see both rows change together. Autocommit = one statement per txn.

vs

Second UPDATE fails

ROLLBACK

BEGIN; UPDATE … A −30; -- ok UPDATE … B +30; -- ERROR 23503 ROLLBACK; -- else stays ABORTED
idwasnow
A100100
B1010

Partial success is not stored. After an error Postgres stays ABORTED until ROLLBACK.

What

Several statements, one commit record. The A in ACID (plate 41). Constraints fail the whole unit (SQLSTATE 23503/23505).

Why

Debit/credit, insert user + profile. A crash after the first INSERT without a txn leaves an orphan row.

Trap

HTTP inside the txn (holds row locks and a pool slot, plate 03). Catching an error and running more SQL without ROLLBACK. Confusing atomicity with isolation (dirty reads, plate 40).
