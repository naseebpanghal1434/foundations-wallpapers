Database3NF · JOIN vs copy

Normalize for writes. Denormalize for reads.

3NF: each fact once — Ada’s email lives in users, not on every order. UPDATE users SET email=… WHERE id=7 cannot disagree with itself. Denormalize: copy user_email onto the order row so a list skips the JOIN. You just bought a cache you must keep in sync (write amplification × N rows).

3NF · one fact

Normalize

users(id PK, email UNIQUE, name) orders(id PK, user_id FK, total) SELECT o.*, u.email FROM orders o JOIN users u ON u.id = o.user_id

Change email once. FKs keep orphans out (plate 17). Writes stay one row.

vs

Copy on the row

Denormalize

orders( id, user_id, total, user_email, user_name) -- list: no JOIN -- email change: UPDATE N rows -- or they lie

Read path is one index scan. Materialized view / summary table = denorm with a refresh job.

What

Normal forms: no repeating groups, no partial/transitive dependency. You don’t have to recite 5NF. Copy = faster read, extra write, drift. OLTP checkout wants normalize; feeds, search, star schemas want denorm or a second store.

Why

Interviews: start normal, denorm when a measured JOIN hurts. “For speed” on day one with no query is not a reason.

Trap

Forgetting the update path (email changes, orders still show the old one). Arrays of ids with no FK: denorm plus no integrity. Two writers updating the copy and the source.
