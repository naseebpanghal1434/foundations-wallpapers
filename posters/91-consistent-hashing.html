SystemHash ring

Only 1/N keys should move.

hash(key) % N assigns shards. Add a node, N becomes N+1, and almost every key changes home — a cache miss storm, a data shuffle. Consistent hashing puts keys and nodes on a ring. A key belongs to the next node clockwise. Add one node, only about 1/N of the keys move.

N=3 → N=4

hash % N

hash(k) % 3 k1→1 k2→2 k3→0 k4→1 hash(k) % 4 k1→1 k2→2 k3→3 k4→0 most keys remapped

The modulus is the cluster size. Change the size, change every address. Fine in a homework shard. Fatal on a live cache.

vs

Nodes own arcs

Ring

hash(node) and hash(key) onto a circle owner = first node clockwise add D between A and B only (A, D] moves to D ~1/N of the keys

Remove B: its arc slides to the next clockwise neighbor. Everyone else keeps their keys.

What

Hash the key and the nodes onto one circle. Virtual nodes: each machine appears many times on the ring so arcs stay even. Dynamo, Cassandra, Ketama, some LBs (plate 35). Redis Cluster uses fixed hash slots — same idea, different picture.

Why

You will add a cache box. The point is not “perfect balance.” It is “don’t reshuffle the fleet.” Plate 37’s shard problem, with a smaller moving day.

Trap

hash % N and “we’ll just rehash.” You just missed on almost every key. No vnodes → one unlucky node owns a huge arc. Hot keys (celebrity user_id) still hammer one node — the ring does not fix that.
